# BeeBike CRM

Прототип внутренней CRM-системы для управления парком самокатов и арендами.
Тестовое задание: проектирование + backend + frontend, с расширениями сверх
базового ТЗ (баланс клиентов, тестовый режим, аналитика в реальном времени).

## Стек и почему именно он

Рекомендованный в ТЗ стек — Laravel/PHP + React — не обязателен, задание явно
разрешает замену с пояснением. Выбран следующий:

| Слой | Технология | Почему |
|---|---|---|
| Backend | **FastAPI** (Python 3.12) | Асинхронный, с встроенной валидацией через Pydantic прямо на границе API — целый класс багов (мусор в теле запроса, некорректные типы) отсекается до бизнес-логики. Автогенерируемая OpenAPI-документация (`/docs`) сразу даёт интерактивный клиент без доп. работы. Быстро пишется и легко читается на ревью. |
| ORM / БД | **SQLAlchemy 2.0 + PostgreSQL** | PostgreSQL — реляционная БД с честными транзакциями и внешними ключами, что важно при списании баланса и смене статусов самоката атомарно. SQLAlchemy 2.0 даёт типизированные модели (`Mapped[...]`) и явный контроль над запросами. |
| Миграции | **Alembic** | Стандарт де-факто для SQLAlchemy, миграции — часть репозитория и CI. |
| Auth | **JWT (HS256, ручная реализация на `python-jose` + `bcrypt`)** | Аналог Sanctum, но без лишней инфраструктуры: один админ-пользователь, простой bearer-токен, минимальная поверхность атаки (нет публичной регистрации). |
| Frontend | **React 18 + Vite + TypeScript** | TypeScript ловит несовпадения типов между API и UI на этапе сборки. Vite — почти мгновенный HMR. Без тяжёлого UI-фреймворка (MUI/AntD) — вся вёрстка на нативном CSS с CSS-переменными, поэтому бандл маленький и тема полностью кастомная. |
| Данные / кеш на клиенте | **TanStack Query** | Готовый `refetchInterval` закрывает требование «real-time обновление статусов» через polling без написания собственного кеша и дедупликации запросов. |
| Карта | **Leaflet + OpenStreetMap** | Не требует API-ключа (в отличие от Google Maps/Yandex Maps) — карта работает «из коробки» после `docker compose up`. |
| Контейнеризация | **Docker Compose** | `db` + `backend` + `frontend` + `adminer` (для быстрого просмотра БД глазами) поднимаются одной командой. |

**Real-time**: выбран polling (5 сек, через `refetchInterval` в TanStack Query)
вместо WebSocket — тот же результат для прототипа, но на порядок меньше кода
и инфраструктуры (не нужен отдельный WS-менеджер соединений, переподключения,
heartbeat). Для продакшена с сотнями клиентов имеет смысл перейти на WebSocket
или SSE.

От себя добавлю: если бы делал систему не как тестовое, а для реального
продакшена, я бы в итоге выбрал WebSocket — не столько из-за нагрузки, сколько
из-за точности. Polling даёт задержку до 5 секунд между реальным изменением
статуса самоката и тем, что увидит оператор в CRM — для одного самоката это
не критично, но при разборе спорной ситуации (например, статус в момент
инцидента) важна именно точность момента обновления, а не экономия кода.
WebSocket даёт обновление статуса практически мгновенно, без этого окна
неопределённости.

## Что реализовано

Базовое ТЗ:

- Самокаты: список (таблица **и** карта), CRUD, фильтр по статусу, поиск по
  номеру/модели, поля точно по ТЗ (номер, модель, статус, заряд, координаты,
  дата обновления).
- Аренды: создание (самокат + клиент), завершение, список активных/завершённых.
- Аналитика на главной: количество самокатов по статусам, число активных
  аренд, средний заряд — обновляется каждые 5 секунд.
- Валидация данных (Pydantic на бэкенде + HTML5/контролируемые формы на
  фронтенде) и единообразная обработка ошибок (understandable сообщения на
  русском, коды 401/404/409/422 по месту).

Сверх ТЗ (по запросу заказчика тестового задания):

- **Баланс клиента.** Аренда привязывается к клиенту по телефону (создаётся
  автоматически при первой аренде). При завершении аренды с баланса клиента
  списывается стоимость (тариф × минуты, округление до полной минуты вверх).
  Страница «Клиенты» показывает баланс и позволяет его пополнить.
- **Пополнение баланса — мок.** Реального платёжного шлюза нет (это не входило
  в ТЗ и не является темой задания): кнопка «Пополнить» либо сразу зачисляет
  сумму, либо возвращает симулированный отказ — в зависимости от настройки
  тестового режима. Это явно указано в интерфейсе, чтобы не создавать
  впечатление реальной оплаты.
- **Настройки → Тариф.** Стоимость минуты аренды редактируется в интерфейсе.
- **Настройки → Test mode.** Тумблер тестового режима (баннер в шапке),
  выбор сценария мок-оплаты (успех / отказ / случайно), кнопка «случайно
  изменить статусы/заряд самокатов» (чтобы наглядно проверить, что polling и
  аналитика действительно обновляются в реальном времени) и кнопка сброса
  демо-данных.
- Тёмная неоновая тема — по референсам приложения, которые прислал заказчик
  (скриншот мобильного UI с чёрным фоном и лаймовым акцентом). Точный логотип
  компании получить не удалось (Instagram отдаёт JS-заглушку без og:image при
  серверном запросе), поэтому использован нейтральный вариант с той же
  цветовой схемой.

## Быстрый старт

Требуется Docker + Docker Compose.

```bash
git clone <repo-url> beebike-crm && cd beebike-crm
cp .env.example .env
docker compose up --build
```

Первый запуск бэкенда сам накатит миграции (`alembic upgrade head`) и засеет
демо-данные (админ, 5 самокатов, 2 клиента, 1 активная аренда) — это
идемпотентно, при перезапуске данные не дублируются.

После старта:

- Frontend: http://localhost:5173
- Backend / Swagger UI: http://localhost:8000/docs
- Adminer (просмотр БД): http://localhost:8080 (сервер `db`, см. `.env` для
  логина/пароля/базы)

Остановить: `docker compose down` (добавить `-v`, чтобы снести и данные тома).

### Локальный запуск без Docker (по желанию)

```bash
# Backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
# поднимите Postgres локально и укажите DATABASE_URL в .env
alembic upgrade head
python -m scripts.seed
uvicorn app.main:app --reload

# Frontend
cd frontend
npm install
npm run dev
```

## Доступы по умолчанию

Задаются в `.env` (`ADMIN_EMAIL` / `ADMIN_PASSWORD`), по умолчанию:

```
email:    admin@beebike-crm.com
password: admin12345
```

**Обязательно смените `SECRET_KEY` и пароль администратора при реальном
деплое** — значения в `.env.example` предназначены только для локальной
демонстрации.

## API

Полная интерактивная документация — `/docs` (Swagger) после запуска бэкенда.
Все эндпоинты, кроме `/api/auth/login` и `/api/health`, требуют
`Authorization: Bearer <token>`.

Кратко:

| Ресурс | Эндпоинты |
|---|---|
| Auth | `POST /api/auth/login`, `GET /api/auth/me` |
| Самокаты | `GET/POST /api/scooters`, `GET/PUT/DELETE /api/scooters/{id}` (фильтр `status`, поиск `search`) |
| Аренды | `GET/POST /api/rentals` (фильтр `status`), `POST /api/rentals/{id}/complete` |
| Клиенты | `GET /api/customers` (поиск), `POST /api/customers/{id}/topup` (мок-оплата) |
| Настройки | `GET/PUT /api/settings` (тариф ₽/мин) |
| Аналитика | `GET /api/analytics/summary` |
| Test mode | `POST /api/admin/reseed`, `POST /api/admin/simulate` |

## Тесты и CI

**Backend** — 26 тестов на pytest против настоящего PostgreSQL (не SQLite —
модели используют нативные типы Postgres: `UUID`, `ENUM`), покрывают auth,
CRUD самокатов, полный жизненный цикл аренды (включая списание баланса и
двойное завершение), пополнение баланса и аналитику.

```bash
cd backend
docker compose up -d db          # или любой локальный Postgres
createdb -h localhost -U beebike beebike_test   # база для тестов, один раз
pip install -r requirements-dev.txt
pytest -v
ruff check .
pip-audit -r requirements.txt
```

**Frontend** — 11 тестов на Vitest + Testing Library (компоненты, контекст
тестового режима, разбор ошибок API).

```bash
cd frontend
npm install
npm run test        # vitest run
npx tsc -b           # типы
npx eslint .          # линт
npm audit
```

**CI** (`.github/workflows/ci.yml`, GitHub Actions): два параллельных джоба —
`backend` (Postgres как сервис-контейнер, миграции, pytest, ruff, pip-audit) и
`frontend` (tsc, eslint, vitest, vite build, npm audit). Запускается на каждый
push и pull request в `main`.

## Безопасность

Что сделано осознанно:

- Пароли хранятся только как bcrypt-хеш (прямая работа с `bcrypt`, без
  `passlib` — у него известна несовместимость с bcrypt ≥ 4.1, из-за которой
  ловится `AttributeError` при инициализации; проще и надёжнее без лишней
  прослойки).
- JWT с ограниченным сроком жизни (`ACCESS_TOKEN_EXPIRE_MINUTES`), секрет
  вынесен в `.env`, не закоммичен (`.env` в `.gitignore`, в репозитории только
  `.env.example` с плейсхолдерами).
- Все мутации данных — через SQLAlchemy ORM с параметризованными запросами
  (включая поиск через `ilike`), инъекции SQL исключены.
- CORS ограничен явным списком origin'ов из конфига, а не `*`.
- Публичной регистрации пользователей CRM нет — только один заранее заданный
  админ, что уменьшает поверхность атаки.
- Pydantic-валидация на границе API: диапазоны для заряда (0–100), координат
  (широта/долгота), сумм пополнения и тарифа — отсекает некорректные данные
  до попадания в БД.

Что проверено сканерами (`pip-audit`, `npm audit`) перед сдачей:

- **Backend**: 0 уязвимостей в проде-зависимостях (`fastapi`, `pydantic`,
  `sqlalchemy`, `psycopg`, `uvicorn`, `bcrypt`, `python-jose`, …). Единственная
  находка — `ecdsa` (транзитивная зависимость `python-jose`, потенциальная
  timing-атака на подпись P-256); проект не использует ECDSA-алгоритмы для
  JWT (только симметричный `HS256`), поэтому код фактически недостижим.
  Апстрим `python-ecdsa` считает side-channel-атаки вне scope и фикса не
  планирует — принято как осознанный риск.
- **Frontend**: изначально находилась 1 critical CVE в Vitest (RCE через
  `--ui` dev-сервер) — устранена апгрейдом Vitest 2 → 4 (мы `--ui` не
  используем, но обновили). Осталось 9 high + 2 moderate, все — dev-only
  транзитивные зависимости ESLint 8 (minimatch/brace-expansion ReDoS) и
  moderate-находки в `react-router` (open redirect / SSR-hydration
  инъекция). ESLint-цепочка никогда не попадает в продовый бандл. React
  Router-CVE требует передавать в `<Link>`/`useNavigate` путь, управляемый
  атакующим, либо SSR — в приложении все маршруты статические и SSR не
  используется, реальная эксплуатация отсутствует; мажорный апгрейд на v7 не
  делался в рамках прототипа, чтобы не тратить время на breaking changes без
  реального риска — зафиксировано как принятое решение.

## Известные ограничения и что делать дальше

Осознанно оставлено за рамками суточного прототипа:

- Нет rate limiting на `/api/auth/login` (защита от подбора пароля).
- Нет refresh-токенов — только один access-токен с фиксированным TTL.
- Нет ролей/прав доступа — все пользователи CRM полноправные админы.
- Баланс клиента может уходить в минус (осознанно, чтобы прототип не
  блокировал демонстрацию завершения аренды из-за нехватки средств) — в
  проде потребует явной бизнес-логики (блокировка аренды при недостаточном
  балансе, овердрафт-лимиты).
- Реального платёжного шлюза нет и не планировался (см. раздел «Что
  реализовано» — пополнение баланса промаркировано как демо-функция).
